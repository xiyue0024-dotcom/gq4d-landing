01同 IP 键阈值：3 还是 5

24 小时内，同一网络出口出现多少个不同号码，才算「批量」。

决策 1一条网线/一个代理出口，带几个号算工作室？

它是什么

「IP 键」是把 IP 收敛成网段后再比较：IPv4 取 /24（如 203.0.113.x 全算一个键）， IPv6 取 /64。这样同一个路由器、同一个代理池出口、同一个运营商 CGNAT 段，会落到同一个键上。 阈值就是：这个键在 24 小时内出现多少个不同 WhatsApp 号码，才触发「同网络批量」信号。

具体做什么

  • 每次请求把 IP 键 + 号码 + 时间 记入缓存计数（不读表，毫秒级）。
  • 24 小时窗口内，该键的不同号码数达到阈值 → 当前请求加 40 分。
  • 10 分钟内达到 3 个不同号码 → 触发短窗聚集，整批封禁（这是另一条规则，与本题无关）。
  • 该分数不单独构成拒绝，需叠加机房 ASN、时区异常、秒填等信号才越过 60 分线。

实际作用

这是抓「一条网络批量进线」的第一道网。工作室常见做法是一条家宽 + 多张卡 + 多开分身， 号码不同、设备指纹可能被改，但出口 IP 往往懒得换。阈值越低，越早发现；但公共网络里的真实客户也会被算进去。

场景 A · 工作室
一条家宽，3 个 WhatsApp 号，上午 10 点各点一次进线。
阈值 3 → 第 3 个号加 40 分，若同时是机房/时区异常 → 拒。
阈值 5 → 三个全部放行。
场景 B · 公共 WiFi
雅加达一家咖啡馆，一天内有 4 位顾客看到广告并点击。
阈值 3 → 第 3、4 位各加 40 分；若他们手机正常，分数不到 60，仍放行。
阈值 5 → 无人加分。
场景 C · CGNAT
印尼移动运营商大量用户共享同一出口段，一个 /24 可能有几十个真实用户。
阈值 3 会让这个段长期处于 +40 状态；因此必须保持「只计分、不硬拒」，否则整片误杀。

代价与风险

取 3：公共网络误伤概率上升 取 5：工作室每 IP 放 2 个号即可绕过 CGNAT 下必须只计分不硬拒

建议

建议
取 3，且保持「只加 40 分、不单独硬拒」。这样既能在工作室出现的早期把它推到 60 分线附近， 又不会因为 CGNAT 或咖啡馆 WiFi 直接封掉真实客户。若上线后发现工作室改用「每 IP 2 个号」， 再把阈值降到 2，或对「同 IP + 同设备型号」组合改为硬拒。
// 3_Risk.gs · CFG.RISK
IP_MULTI_24H: 3, // 24h 内同 IP 键不同号码数阈值
IP_MULTI_SCORE: 40, // 达到阈值加多少分
IP_MULTI_HARD_DENY: false // 是否单独硬拒（建议 false，防 CGNAT 误杀）

02是否上 PoW 挑战

评分 35–59 的「可疑但不确定」流量，给一次自证机会，而不是直接判死。

决策 2拿不准的请求，是放还是杀？PoW 提供第三条路。

它是什么

PoW（Proof of Work，工作量证明）是让浏览器算一道很小的数学题：找一个随机数，使 SHA-256(随机数 + 挑战串) 的结果前若干位为 0。难度 18 bit 意味着平均要算约 26 万次， 手机大约 100–300 毫秒，人几乎感觉不到；但脚本要批量请求，就得为每一条付出同样的 CPU 时间。

具体做什么

  • 评分落在 35–59：不直接拒，返回一个挑战串。
  • 浏览器用 Web Crypto 计算，解出后带着答案重新请求。
  • 服务端验证答案：正确 → 放行；错误或超时（8 秒）→ 拒绝。
  • 挑战串一次性、绑定 device_id、TTL 2 分钟，不能复用。
  • 老设备不支持 crypto.subtle 时按配置降级（建议降级放行，不卡死真实用户）。

实际作用

它把「判定」从二选一变成三选一：确定安全 → 放行；确定恶意 → 拒绝；拿不准 → 让对方付一点成本。 对真人几乎无感，对脚本农场是实打实的成本上升，而且每次挑战都不同，无法预计算或缓存复用。

场景 A · 真实客户（低端机 + 内置浏览器）
2019 年安卓机，从 Instagram 内置浏览器打开。WebView 天生没有 window.chrome、plugins 为 0，评分 40。
没有 PoW：要么误杀（阈值降到 35），要么放行（阈值升到 60）。
有 PoW：200ms 解出 → 放行，客户无感。
场景 B · 脚本直调
Python 脚本用 requests 直接请求判定端点，没有浏览器环境，无法执行 JS。
有 PoW：无法计算 → 拒绝。
没有 PoW：只要伪造字段像样，就可能拿到账号。
场景 C · 批量开页
工作室用 Puppeteer 同时开 200 个页面，每个都要解一次 PoW。
单条多花 200ms，200 条多花 40 秒 CPU；并发一高就拖慢，且更容易被行为信号抓到。

代价与风险

前端多约 40 行代码 极老设备可能不支持 Web Crypto 真人多等 100–300ms 挑战逻辑本身要防重放

建议

建议
上。难度取 18 bit（手机约 100–300ms），挑战区间 35–59，超时 8 秒。 老设备不支持时降级放行而不是拒绝——这类设备占比很低，但误杀真实客户的代价比放过一个脚本更高。
// 3_Risk.gs · CFG.CHALLENGE
ENABLED: true, // 是否启用挑战
MIN_SCORE: 35, // 进入挑战的最低分
MAX_SCORE: 59, // 超过则直接拒绝
DIFFICULTY: 18, // 前导 0 位数，越大越慢
TIMEOUT_MS: 8000, // 超时按拒绝
UNSUPPORTED: 'allow' // 不支持 Web Crypto 时：allow | deny

03判定是否迁到 Cloudflare Worker

从「浏览器直连 Apps Script」改为「浏览器 → 自家边缘 → Apps Script」。

决策 3现在的判定端点，任何人都能直接调用。

它是什么

现在浏览器用 JSONP 直接请求 Apps Script 的 /exec。问题是：Apps Script 的 doGet(e) 拿不到请求头，无法验证请求是不是来自你的页面，也没有原生限流。 迁移后，浏览器只请求自家域名 POST /api/gate，由 Cloudflare Worker 做来源校验、限流、 挑战校验，再带共享密钥转发给 Apps Script。

具体做什么

  • 来源校验：Worker 读 Origin / Referer，不是你的域名直接 403。
  • 边缘限流：按 IP 10 次/分、/24 网段 60 次/分、ASN 600 次/分；超限返回同一张「繁忙」页。
  • 同源 POST：不再需要 JSONP，前端 fetch 直接读 JSON，代码更短。
  • 共享密钥：Worker → Apps Script 带一个密钥，后端只接受来自 Worker 的判定请求。
  • 黑名单快照：Worker 缓存一份只读名单（每分钟刷新），常见请求不必回源。
  • 隐藏后端：Apps Script URL 不再出现在 HTML 里。

实际作用

这是「能不能扛住一次攻击」的分水岭。前面所有判定都跑在 Apps Script 上，而消费者账号每天只有约 90 分钟执行时长；一次每秒 50 次的脚本攻击，几分钟就能把它打爆，之后所有真实用户都会因为 fail-closed 被拒——攻击者不需要骗过判定，只要让你瘫痪就够了。

场景 A · 端点被刷
工作室直接 GET /exec?d={...}&cb=x，每秒 50 次。
现状：几分钟打爆日配额 → 全体 fail-closed，真实客户全部被拒。
迁移后：49/50 在边缘被 429 挡掉，只有 1 次进后端。
场景 B · URL 被贴到爬虫池
竞争对手把你的 /exec 地址丢进轮询池，持续低频调用。
现状：无法区分来源。
迁移后：Origin 不是你的域名 → 直接 403。
场景 C · 真实客户网络慢
印尼 4G 用户，JSONP 往返约 700ms，加软拦 3.5s，共 4.2s 才跳转。
迁移后边缘就近响应约 150ms，总计 3.65s；且延迟可下调，体感更顺。

代价与风险

多一个 Worker 路由（已有 Worker，只需加路径） 需要一把共享密钥 排障多一跳 前端要从 JSONP 改 fetch

建议

建议
上。不加的话，前面所有判定都可能被「打爆配额」一招废掉；而且这是唯一能真正验证请求来源的位置。 工作量不大：Worker 已经有 IP 回显路由，加一个 /api/gate 即可。
// 前端 CONFIG
gateUrl: 'https://你的域名/api/gate' // 同源，不再是 script.google.com

// Worker · wrangler.toml
GATE_ORIGIN: 'https://你的落地页域名'
RATE_IP_PER_MIN: 10, RATE_SUBNET_PER_MIN: 60, RATE_ASN_PER_MIN: 600
